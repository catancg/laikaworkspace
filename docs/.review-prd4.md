# Review — PRD 4 (Bulk knowledge loading)

Adversarial read, checked against the actual backend code (`soylaika.backend/src/faq/faq.controller.ts`,
`tenants.controller.ts`, backend `CLAUDE.md`) and against PRD 1/2/3. Two errors and two gaps the
requester already found are not repeated here (route count "seven" vs nine; PRD 2's CSV-only
framing; the missing transaction in `upsertBatch`; the implied double-upload in preview/confirm).

---

## 1. Does §4's argument hold?

No — not as stated. Two independent problems, one philosophical and one structural.

**Philosophical: "who wrote it" is being used as a proxy for "has been verified," and those are
not the same act.** The table in §4 treats template-authorship as evidence of truth-checking: the
client typed it, so the client is "the authority on whether it is true." But typing a cell is not
the same act as verifying the fact in that cell. A client (or, more likely, an employee filling in
a spreadsheet handed to them) can transcribe a stale price policy, a warranty term a previous owner
set and no one revisited, or something they misremember — with exactly the same confidence and
exactly the same lack of a check as an LLM extracting from a stale document. The argument correctly
identifies that *only the client* can catch "the warranty is six months, not nine" — but it then
assumes the act of uploading a filled template *is* that catch. It isn't. Nothing in the pipeline
distinguishes "the client re-derived this from first-hand knowledge just now" from "the client
copy-pasted this from a document they haven't looked at since 2019." The mitigation the document
offers for mode B (someone compares the answer to a cited excerpt) has no analogue for mode A at
all — there is no equivalent "did you actually check this" gate. The document treats this as
solved by role; it should treat it as unsolved and say so.

**Structural: the system as designed cannot even tell you who wrote a mode-A row.** Nothing in
the `FaqChunk` schema (checked against PRD 1 §5 and the shipped deltas in PRD 1 §15) records an
uploader or author — there is `source_type`, `source_ref` (the batch id), `reviewed_by` /
`reviewed_at` (who *approved*), but no `uploaded_by` / `created_by`. PRD 3 §12 already flags this
exact blind spot for manual *edits* ("a superadmin edits the wrong tenant, and nothing records
that they did"). PRD 4 reintroduces the identical gap for *imports*, and here it is load-bearing
rather than incidental: §4's entire authority model is "authority depends on who wrote the
content" — and the system cannot record who wrote the content. Concretely: the motivating case in
§1 is the Ideas Todo Terreno file, 28 articles, "one to two hours of typing into a dialog, field by
field." Given that "any screen at all" is confirmed missing today, that typing was almost certainly
done by an implementer transcribing the client's document into the CSV template — not by the
client. By the letter of §4's table this is "Template the client filled in" → client approves, but
the actual human at the keyboard was staff, not the client, and nothing in the data model
distinguishes this case from a genuine client self-upload. §4's own mechanism cannot tell the two
apart after the fact, which means the policy it proposes is currently unenforceable and
unauditable, not just debatable.

**The mode A/B split is clean in the abstract and does not survive contact with phase A.** Every
Mode-A row landed before phase E ships (i.e., everything phase A, B, C, D produce) is staff-typed
on the client's behalf, exactly the ambiguous middle case above. §4 presents the table as if it
already governs today's behavior; it only starts to apply, even loosely, once phase E ships a
client-facing upload screen — three phases later.

## 2. Is the phasing honest?

**Mostly, with one large exception: the phase that would make §4's central claim true is never
scheduled.** §4 says "the client can approve their own." Phase E ships "client-facing upload
(tenant admin), mode A only" — but *uploading* and *approving* are different actions, and nothing
in phases A–F, nor anywhere in PRD 3, builds a tenant-facing approve/reject screen. PRD 3 gates
its entire review-queue UI to the superadmin panel (`@Roles('superadmin')` at the controller
class level, confirmed in `tenants.controller.ts`) and explicitly lists a tenant-facing version as
a non-goal, "a separate decision" (PRD 3 §3, §13 Q1 — which asks almost this exact question and
leaves it open). So when phase E ships: the client uploads, rows land `PENDING_REVIEW` under a
`source_ref`, and then — with no tenant-facing approve screen anywhere in scope — the only human
who can currently press "approve" via any built UI is a superadmin. Phase E, as scoped, does not
deliver the right §4 argues for; it delivers the same superadmin-gated approval as today, with a
nicer upload path. That is a materially smaller (and different) feature than the document's own
thesis, and the phasing table does not flag the gap.

(Note: the backend primitives are *not* the blocker — `POST /api/faq/:id/approve` already accepts
role `admin`, and a tenant admin's JWT already resolves to their own tenant DB via subdomain, per
`faq.controller.ts`. This is purely a missing UI/route surface, not a missing capability. But the
document never notices it needs one.)

**Second, smaller issue: §11 calls the flagging/reporting channel "not optional," but no phase
ships it.** See §5 below (internal contradiction).

**Is Phase C really independent, as claimed?** Structurally yes, and it may be *smaller* than the
document implies: `GET /api/faq` in the current controller has no `@Roles` guard at all — any
authenticated tenant user can already call it and get the full list. Phase C may need zero new
backend work, just a frontend screen. The document doesn't establish this (unlike phase A, where it
carefully checks whether the existing endpoint is reachable), so an implementer would either
duplicate work or discover the free lunch by accident. Also unaddressed: if visibility is meant to
be `admin`-only ("the tenant's own admin role," §5), the underlying endpoint currently enforces no
such restriction — anyone with a valid tenant token, any role, can already read everything via a
raw API call. Low risk, but the document asserts a role boundary the backend doesn't have.

**Is Phase A shippable alone, safety-wise?** Yes on its own terms. It doesn't need to be re-litigated
here beyond noting it's the first time the known non-transactional write path becomes reachable by
real usage rather than sitting dormant — worth being aware of when prioritizing B relative to A,
though the PRD is not wrong that A alone is valuable.

**One route-shape problem cuts across every phase from A onward** — see §4 (hand-wave) below; it's
as much a phasing problem as a design problem, because phase A and phase E are described as if they
share one endpoint that, per PRD 3's own established pattern, they structurally cannot.

## 3. What is missing entirely

Ranked by consequence:

1. **A tenant-facing approve/reject surface.** Covered in depth above. Without it, §4's central
   claim ("the client can approve their own") has no delivery mechanism in any phase of any of the
   four PRDs. This is not a minor omission — it's the thing that would make the document's own
   thesis true, and it's absent from the phasing table, the open questions, and the risks section.

2. **Any actor/audit trail for imports.** No `uploaded_by` on `FaqChunk`, no record of which user
   (client admin vs. superadmin, and if superadmin, acting on whose instruction) ran a given
   import. This directly undercuts §4 (see §1 above) and repeats, for bulk import, the exact
   blind spot PRD 3 §12 already flagged for manual edits — a PRD explicitly about giving business
   users write access to their own knowledge base should not ship without knowing who touched it.
   PRD 4 doesn't mention this once, despite §4 being an entire section about who is allowed to do
   what.

3. **Withdrawing or deleting a whole batch.** Nothing in this document, or in PRD 1/2's schema,
   offers a batch-level undo. `DELETE /api/faq/:id` is per-row. If a client uploads the wrong file,
   uploads to a re-opened tab with stale data, or a superadmin loads one tenant's file into another
   tenant's import screen (a very real risk once cross-tenant superadmin tooling exists — see PRD 3
   §9's warnings about exactly this class of mistake), the only recovery path is deleting rows one
   at a time, found by scrolling a list, with no "these all came from `import:<uuid>`, undo them"
   button. Given `source_ref` already groups a batch for review, grouping it for deletion is nearly
   free and is a natural companion to the "direct link to the queue filtered by that source_ref"
   the document already proposes in §6.4.

Runners-up, worth a line each rather than a full slot: **concurrent uploads** are not dangerous
(batch ids are UUIDs, no shared mutable import state) but the preview/confirm gap means a dryRun's
"will pass" prediction can go stale if another import or edit lands between preview and confirm —
unaddressed, low-severity. And **what the business sees when a superadmin loads on its behalf** is
answered in principle by §5 ("regardless of who loaded it") but not in practice: §5 scopes
visibility to "every active chunk," and a batch a superadmin has just loaded is `PENDING_REVIEW`
before anyone touches it — it is unclear whether "active" in §5 means the `active` boolean column
(which defaults true regardless of review status, so pending rows would show) or "currently served
to customers" (approved + active, so they would not). If it's the latter, the business has no
visibility into exactly the batch this document is most likely to produce during onboarding: a
pile of superadmin-loaded, not-yet-reviewed rows.

## 4. Where does it hand-wave?

**The single route pair in §6.3 cannot serve both audiences the document assigns to it.**
`POST /tenants/:slug/faq/import?dryRun=true` is presented as *the* mode-A endpoint, used by phase A
(superadmin) and, implicitly, by phase E (tenant admin) — the document never distinguishes them.
But PRD 3 §4.1 establishes, for exactly this codebase, that `/tenants/:slug/*` routes are
superadmin-only at the controller class level, and PRD 3 §9 rule 3 states outright: "Nothing in
these screens should ever call `/api/faq/*` directly — that path is for a tenant acting on itself"
— implying, correctly, that a tenant's own screen must go through `/api/faq/*`, not
`/tenants/:slug/*`. A tenant admin cannot reach a superadmin-gated route. That means phase A and
phase E need *two different endpoints* (one already exists in tenant-context form, confirmed
reachable by role `admin` today; one is the new superadmin-mirror route), each needing its own
`dryRun` support, and the document specifies only one, as if it covers both. This is invented by
the implementer either way — cheaply if they notice it, expensively if they build phase E believing
phase A's route can be reused with a different frontend.

**Whether the mode-A/mode-B split is enforced anywhere, or just a UI convention.** §4 says "the two
ingest modes do not share one screen." Fine as a UI rule. But is there a backend check that a
mode-B (`source_type: DOCUMENT`) chunk cannot be approved by a tenant admin, or is that purely
"the screen doesn't offer the button"? PRD 3's existing approve endpoint takes only an id and a
patch — nothing in it inspects `source_type` to refuse a tenant-admin approval of extracted
content. If mode B ever becomes reachable from a tenant-facing screen (even by a future
well-intentioned extension), there is no server-side backstop matching the one the document argues
is essential. Worth being explicit that the mode split is a client-side/route-level convention only,
not an invariant enforced at the data layer the way `review_status`-gates-retrieval is.

**Who resolves an unresolved `{{placeholder}}` for a mode-A row, and how does the client see it?**
§6.3 says a placeholder blocks at approval, not at import preview (only a warning). For mode B,
PRD 2 §8 has a whole mechanism (resolve from `BusinessProfile`, else surface in review). PRD 4
never says what happens when a client's own template row contains a placeholder — does their
preview screen show it as a warning they can ignore, then discover at approval time (which, per
finding #1 above, they likely can't even reach) that it's blocked? The document is silent.

## 5. Internal contradictions

- **§11 vs. the phasing table (§9).** §11 states plainly: "Visibility without a channel is worse
  than no visibility... The reporting path in §5 is not optional." §5 proposes the flag/comment
  channel as one of the three concrete things visibility delivers. Yet Phase C — the phase that
  ships §5's visibility — is scoped only as "Read-only knowledge view for the tenant's admin role."
  No phase (C through F) builds the flag/comment channel. The document declares a mechanism
  mandatory and then never schedules it. This is the sharpest contradiction in the document.

- **§4 vs. PRD 3 §13 Q1.** PRD 3 explicitly poses "Should a tenant admin get a read-only view of
  their own knowledge base?" as an *open question for PRD 3* to decide. PRD 4 answers it (§5) as if
  settled, without citing PRD 3 §13 at all (it cites PRD 3 §3, a different section, for a different
  point). A document that resolves another document's stated open question should say so and carry
  forward the considerations raised there — PRD 3 §9's rules about tenant-vs-superadmin route
  boundaries are directly relevant to phase C/E's new screens and go unmentioned.

- **§4 vs. PRD 2 §5.** PRD 2's own review-workflow recommendation is a blanket "the tenant reviews
  their own content, with two backstops" — it does not condition this on origin. PRD 4 §4 narrows
  this into a two-tier split by mode. That's a reasonable refinement, but PRD 4 doesn't present it
  as amending PRD 2 §5; it reads as though it's the first document to raise the question, when PRD
  2 already made (and left semi-open, per its own §12 Q2) a related recommendation.

## 6. Is anything over-specified?

- **§6.2's XLSX proposal is written with implementation-level specificity** (four columns labelled
  in Spanish, instructions sheet, three example rows) for a decision the document itself defers to
  an open question (§13 Q1, XLSX vs. Google Sheet). Fine to have a recommendation, but presenting
  the "to be decided" alternative with a full spec and the alternative with one line ("Cheaper
  alternative... no code, more steps") reads as a decision dressed as a question. If it's genuinely
  open, both options deserve equal specificity, or the recommendation should just be stated as a
  recommendation rather than as the default plan.

- **The literal route signature in §6.3** is over-specified relative to how unsettled the
  authorization model behind it actually is (see §4 above). Naming an exact endpoint before
  resolving which controller/guard it belongs to gives false confidence that the hard part (who's
  allowed to hit it) is done.

Nothing else reads as scope that doesn't belong; §5's inclusion inside a "bulk import" PRD is a
reasonable editorial call given how directly §4's authority question depends on it, even though it
answers a question PRD 3 formally owns (see §5 above).

---

## Bottom line

The mechanical parts of this document (§6, §7, §8, phasing A/B/D/F) are in good shape and mostly
match the code. The part the document itself calls "the most consequential question" (§4/§13 Q4)
is also the part that doesn't hold up: the authorship-based approval split is unenforceable in the
current data model (no uploaded-by field), unproven by the one worked example in the document
(the motivating Ideas Todo Terreno case is staff-typed, not client-typed), and — most importantly —
never actually gets built, because no phase in this document or PRD 3 ships a tenant-facing
approval screen. Phase E as scoped ships client uploads into a queue only a superadmin can clear,
which is real value but not the value §4 argues for.
